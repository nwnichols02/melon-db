Sync is split across the engine and orchestrator: **`@melon-db/db`** owns change extraction and remote apply; **`@melon-db/sync`** owns the pull/push loop, retry, and status machine.

For usage examples see the [Sync guide](/docs/sync). For the split-package rationale see [ADR-002](/docs/architecture/decisions#adr-002-split-storage-and-sync-packages).

## Components

```mermaid
flowchart LR
  subgraph clientApp ["Client app"]
    MDB["MelonDatabase sync"]
    Outbox["_melon_sync_outbox"]
    Sync["@melon-db/sync"]
    Hooks["useSync hooks"]
    MDB --> Sync
    Outbox --> Sync
    Sync --> Hooks
  end

  subgraph backend ["Backend"]
    Server["@melon-db/sync-server"]
    PG["PostgresSyncStore"]
    Server --> PG
  end

  Sync -->|"pull / push HTTP"| Server
```

| Piece | Owner | Role |
|-------|-------|------|
| Outbox table | SQLite adapter + engine | Queues local creates/updates/deletes with optional `pendingFields` |
| `getLocalChanges()` | `@melon-db/db` | Watermelon-compatible change payloads for push |
| `applyRemoteChanges()` | `@melon-db/db` | Applies pull results with conflict policy |
| `synchronize()` | `@melon-db/sync` | Pull → apply → push → ack → checkpoint |
| Checkpoint store | `@melon-db/sync` | Persists `lastPulledAt` and schema version |
| Reference server | `@melon-db/sync-server` | In-memory or Postgres HTTP backend for dev |

## Pull/push sequence

```mermaid
sequenceDiagram
  participant App
  participant Sync as "melon/sync"
  participant DB as MelonDatabase
  participant Backend

  App->>Sync: synchronize()
  Sync->>Backend: pullChanges
  Backend-->>Sync: changes + timestamp
  Sync->>DB: applyRemoteChanges
  Sync->>DB: getLocalChanges
  Sync->>Backend: pushChanges
  Sync->>DB: markLocalChangesPushed + checkpoint
```

## Conflict resolution flow

When a remote row collides with a local row (or outbox entry), `applyRemoteChanges` dispatches by policy:

```mermaid
flowchart TD
  Start[Remote change] --> Local{Local row?}
  Local -->|no| Insert[Insert remote]
  Local -->|yes| Outbox{Outbox?}
  Outbox --> Policy{Policy?}
  Policy --> SW[server-wins]
  Policy --> CW[client-wins]
  Policy --> MB[merge-by-field]
  Policy --> Custom[custom]
```

Policies shipped in Phase 15–18:

- `server-wins` (default)
- `skip-existing`
- `client-wins`
- `last-write-wins` (requires `syncTimestampField`)
- `merge-by-field` — uses `pendingFields` on outbox entries (Phase 17)
- `custom` — pluggable `conflictResolver` (Phase 18)

## Migration-aware sync

Schema version travels with checkpoints. On pull, `buildPullMigration()` can describe client-side migration steps when server schema version advances. Strict vs lenient policies control whether sync pauses on mismatch.

## Status machine

`synchronize()` reports: `idle` → `pulling` → `pushing` → `complete`, with `retrying`, `paused` (offline), or `failed`. Retry uses exponential backoff with jitter; `AbortSignal` cancels in-flight pull/push.
